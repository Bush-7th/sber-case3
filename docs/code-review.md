# Ревью текущей реализации

Дата: 10.10.2026. Проверен checkout `0b13752` в `C:\projects\sber-case3`. Перед проверкой рабочее дерево было чистым. Производственный код не изменялся.

Проверены исходники backend и frontend, DTO и оба HTTP-клиента, миграции, сессии/права/CSRF, транзакции хранилища, формы специалиста и администратора, просмотрщик, каталог, тесты, Dockerfile, Compose и инструкции запуска. Автоматически сгенерированные файлы проверены на соответствие источникам.

**Вывод:** инфраструктура и вход имеют работающую реализацию, но проект пока нельзя считать готовым сквозным приложением. Обработка документов и прикладные операции backend явно отложены и возвращают 501. Отдельно от этой заявленной незавершённости найдены **шесть воспроизводимых дефектов** в уже написанном коде.

Приоритет P2 означает ошибку, которую следует исправить в ближайшем цикле: она проявляется в конкретном сценарии и имеет обходной путь либо ограниченную область влияния. P0/P1 среди подтверждённых дефектов текущего реализованного объёма не назначены. Это не означает готовности всего продукта к приёмке.

## Подтверждённые дефекты

### R01 · P2 · Настройки заявки не могут восстановиться после конфликта ревизий

Код: [PackageWorkspace.tsx](../frontend/src/features/packages/PackageWorkspace.tsx#L26), строки 23–34; [queries.ts](../frontend/src/shared/api/queries.ts#L54), обработка 409.

`Configuration` один раз запоминает `item.input_revision` через `useState` без setter. После ответа 409 запрос заявки обновляется, но `expected_revision` открытой формы остаётся прежним. Изменение полей и повторное сохранение не помогают; текст ошибки при этом сообщает, что актуальная версия уже загружена.

**Воспроизведение:** открыть настройки ревизии 2, изменить заявку в другой вкладке до ревизии 3, сохранить форму, получить 409, повторить сохранение. В браузере подтверждено: заголовок показывает ревизию 3, оба PATCH отправляют `expected_revision: 2`.

**Последствие:** пользователь застревает в повторяющемся конфликте. Сейчас обход — закрыть и заново открыть настройки, потеряв локальные правки.

**Исправление:** хранить исходную ревизию редактирования и явно предлагать сверить/применить актуальный снимок после 409. После подтверждения обновлять базовую ревизию с сохранением согласованных правок. Не подставлять новую ревизию автоматически: это уберёт защиту от перезаписи чужих изменений.

### R02 · P2 · Повтор решения после 409 продолжает использовать старую ревизию

Код: [DecisionPanel.tsx](../frontend/src/features/decisions/DecisionPanel.tsx#L25), строки 25–45.

Ревизия формы меняется только при редактировании пустого основания (`if (!reason)`). После конфликта основание уже непустое, поэтому даже его изменение и повторное подтверждение не обновляют `expected_revision`.

**Воспроизведение:** начать решение на ревизии 2, изменить состав заявки до ревизии 3, получить 409, дополнить основание, снова подтвердить и отправить. В браузере обе команды отправили ревизию 2 при актуальной ревизии 3.

**Последствие:** штатный повтор решения невозможен. Обход — полностью очистить основание и набрать его заново либо перезагрузить страницу.

**Исправление:** показывать конфликт и отдельное действие «Применить актуальную ревизию после сверки». При смене основы сбрасывать подтверждение, сохраняя текст основания; обновление базовой ревизии должно быть явным.

### R03 · P2 · Подтверждение решения сохраняется при смене отчёта, а команда ссылается уже на новый отчёт

Код: [DecisionPanel.tsx](../frontend/src/features/decisions/DecisionPanel.tsx#L24), строки 24–35; [PackageWorkspace.tsx](../frontend/src/features/packages/PackageWorkspace.tsx#L107), polling отчёта.

Флаг `confirmed` сбрасывается при изменении действия/основания и после успеха, но не при смене отчёта или его прогресса. `report_id` вычисляется из текущего `currentRun` непосредственно при отправке. Частичные результаты продолжают обновляться, пока пользователь заполняет решение.

**Воспроизведение:** прочитать частичный отчёт A, заполнить основание и отметить подтверждение, дождаться новой версии отчёта B того же запуска и ревизии, отправить решение. В браузере подтверждение осталось отмеченным, а команда отправила `report_id: B`, хотя отметка была сделана на A.

**Последствие:** ссылка в журнале решения может указывать на отчёт, который специалист не подтверждал. При потере ответа изменение `report_id` также изменит fingerprint команды и ключ повторной отправки.

**Исправление:** фиксировать подтверждённую основу — ревизию, run ID, report ID и при необходимости progress version. При изменении этой основы требовать повторного подтверждения. Для повтора после неоднозначного сетевого результата сохранять исходное тело команды и её ключ до выяснения результата.

### R04 · P2 · Частичный приём путает разные файлы с одинаковым именем

Код: [UploadPanel.tsx](../frontend/src/features/upload/UploadPanel.tsx#L32), строки 30–37.

После загрузки локальный список фильтруется только по имени отвергнутого файла. Однако выбор допускает разные файлы с одинаковым именем: проверка дублей учитывает также размер и `lastModified`.

**Воспроизведение:** выбрать два различных `same.pdf`, принять один и отклонить второй. Браузерный сценарий показал: после ответа «Принято файлов: 1» в очереди остаются оба файла вместо одного.

**Последствие:** следующий клик повторно отправляет уже принятый файл с новым idempotency key, создавая возможность дублирования и лишней обработки.

**Исправление:** идентифицировать элементы загрузки стабильным клиентским ID или индексом batch, возвращаемым и для принятых, и для отвергнутых элементов. Одного имени для сопоставления недостаточно. Временный вариант — явно запрещать неоднозначные совпадения имён в одном batch.

### R05 · P2 · Отсутствие дополнительного документа показывается как ошибка

Код: [RunResult.tsx](../frontend/src/features/results/RunResult.tsx#L180), строки 177–184.

Для статуса `missing` компонент различает только `conditional` и все остальные виды требований. Поэтому `optional` получает оформление `error`. Серверный `RequirementResult` допускает для optional информационный уровень; текущая UI-схема не сохраняет severity результата комплектности.

**Воспроизведение:** отобразить результат с `kind: optional`, `status: missing`, `severity: info`. В браузере фактический класс индикатора — `badge error`.

**Последствие:** дополнительный документ визуально превращается в обязательный дефицит и может повлиять на решение специалиста.

**Исправление:** передавать и отображать серверный severity результата. Если временно остаётся вычисление по kind, обработать optional отдельно как информационный/нейтральный случай.

### R06 · P2 · Bootstrap создаёт учётные записи, которые не принимает форма входа

Код: [cli.py](../backend/src/app/runtime/cli.py#L62), строки 62–64; [schemas.py](../backend/src/app/http_api/schemas.py#L129), строки 129–131.

В bootstrap проверяется непустота `username.strip()`, но сохраняется исходное имя с пробелами. В `SessionCreate` пробелы удаляются до поиска пользователя. Также bootstrap ограничивает пароль только снизу (12 символов), тогда как вход ограничен 1024 символами сверху.

**Воспроизведение на реальной PostgreSQL в отдельной временной БД:** bootstrap успешно создал специалиста с именем ` specialist ` и администратора с паролем длиной 1025. Вход специалиста с тем же именем вернул 401 `invalid_credentials`, вход администратора — 422 `invalid_command`.

**Последствие:** provisioning завершается успешно, но пользователь не может войти. Readiness проверяет наличие активных ролей и не обнаруживает такие недоступные учётные записи.

**Исправление:** нормализовать имена до проверки уникальности и сохранения, проверять пароль в диапазоне 12–1024. Применять одинаковые правила к provisioning и входу. Проверять совпадение имён уже после нормализации.

## Блокеры интеграции, уже отмеченные документацией

Это не скрытые дефекты готовых обработчиков: [limitations.md](limitations.md) и [frontend-contract.md](frontend-contract.md) прямо описывают незавершённость. Однако устранение только шести ошибок выше не сделает приложение рабочим.

**UI продолжает использовать предварительные DTO.** Сгенерированные типы CON01 и `openapi-client.ts` существуют и проходят проверки, но экраны импортируют другой `client.ts`. Поэтому зелёный `api:check` подтверждает соответствие сгенерированных типов backend, а не соответствие реального UI серверу.

## Безопасность и эксплуатация

В реализованной части проверены отказ без сессии, разграничение ролей, CSRF и Origin, Secure-cookie на HTTPS, отзыв/истечение сессии, отключение пользователя, сохранность сессий после перезапуска API. Не обнаружен подтверждённый обход этих проверок в текущих маршрутах. Прикладные маршруты пока не выдают данные, поэтому защищённость реальных ресурсов после их подключения ещё не доказана.

Пароли хешируются Argon2id, секреты сессии и CSRF хранятся хешированными, ответы/логи не отражают секретные входные значения, ошибки имеют correlation ID. Хранилище проверено на rollback, сохранность байтов, удержание ссылок и конкурентный повтор immutable put.

**Открытые эксплуатационные вопросы:**

- В текущем коде и Nginx нет ограничения частоты входа. Контрольные 12 неверных попыток подряд все получили 401. Каждая попытка запускает Argon2 и обращение к БД. Перед доступом из недоверенной сети нужен лимит попыток/одновременных проверок и проверка поведения при превышении; прогон 12 попыток не является нагрузочным тестом.
- `client_max_body_size 0` делегирует лимиты API, но общего ограничения тела запроса пока нет. До подключения загрузки нужны ограничения размера, количества файлов и подготовки. Ограничение длины поля Pydantic не ограничивает размер JSON до его разбора.
- Ownership-policy существует и проверена отдельно. После реализации прикладных обработчиков каждый маршрут исходника/превью/таблицы/отчёта должен использовать реальные факты владельца, а не только проверку роли в middleware.
- Readiness честно сообщает `pipeline_ready: false`. Docker healthcheck проверяет liveness; состояние контейнера «healthy» не подтверждает готовность документного конвейера.

## Рекомендуемая последовательность

1. Согласовать конечный API и подключить используемый экранами клиент к CON01. Прикладные обработчики и UI должны иметь один проверяемый контракт.
2. Исправить R01–R03 вместе как жизненный цикл редактирования/подтверждения и повторов; добавить сценарии 409 и обновления отчёта.
3. Исправить сопоставление batch-элементов R04, severity R05 и нормализацию bootstrap R06.
4. Подключить backend-процессинг, ограничения HTTP и frontend в Compose; выполнить реальную сквозную приёмку на документах, включая сбои и перезапуск.
