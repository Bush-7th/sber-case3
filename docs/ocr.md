# OCR01 — удалённый olmOCR и сохранённое содержимое

M03 задаёт [OcrPort и типы источника](../backend/src/app/modules/assets/ocr.py), готовит PDF/изображения и сохраняет результат. M06 реализует [OlmOcrClient](../backend/src/app/modules/inference/olmocr.py); M15 собирает зависимости. Новый логический модуль не добавлен. Классификация и JSON полей остаются задачами отдельного Qwen/Ollama-адаптера.

## Контракт и настройки

На 10.10.2026 повторно сверены [OpenAPI](https://ocr.ilons.ru/openapi.json) и GET `/health`: 200, status=ok, model=allenai/olmOCR-2-7B-1025-FP8, layout=true. POST `/ocr` принимает multipart `file` и возвращает text/plain; границу multipart формирует httpx. Адаптер читает response.text, сохраняет Markdown без изменения и принимает также text/markdown из руководства. JSON/HTML в успешном ответе или пустой текст считаются ошибкой. `/ocr/stream` не используется.

```dotenv
OLMOCR_BASE_URL=https://ocr.ilons.ru
OLMOCR_API_TOKEN=
OLMOCR_TIMEOUT_SECONDS=300
OLMOCR_PROFILE_REVISION=1
OLMOCR_MAX_INPUT_BYTES=50000000
OCR_PREPARATION_MAX_PAGES=200
```

Токен, если задан, передаётся только в x-api-token. ILONS_API_KEY не используется для OCR. URL подключения не может содержать credentials/query; перенаправления запрещены. По умолчанию клиент не наследует настройки прокси из окружения. Тайм-аут ограничивает как сетевое ожидание, так и полную длительность одной попытки; 300 секунд остаются клиентской настройкой, а не доказанным лимитом сервера.

50 000 000 байт и 200 страниц — начальные ограничения подготовки приложения. Они не доказывают фактические ограничения удалённого развёртывания. OLMOCR_PROFILE_REVISION увеличивается при изменении конфигурации сервиса, которое не отражено в health/model/version/layout. Пустой OCR-токен успешно прошёл один реальный запрос; наличие токена для других сценариев и фактические максимальные размеры ещё требуют проверки.

Локальный AppContainer не создаёт OCR-клиент автоматически и не вызывает сеть. Standalone CLI ниже явно обращается к удалённому OCR для диагностики; это не fallback локального анализа. Рабочий pipeline подключит этот адаптер только во внешнем профиле в INT01.

## Подготовка и сохранение

Подготовка поддерживает PDF, PNG, JPG/JPEG. DOC/DOCX/XLS/XLSX напрямую отвергаются; их конвертер и стратегии подключаются в FMT01. HEIC в обязательный объём этого адаптера не включён.

Для PDF каждая страница адресуется номером исходника с 1. Нативный непустой текст обходит OCR. Для страницы без текстового слоя создаётся отдельный одностраничный PDF; ответ относится только к этой исходной странице. Изображения проверяются Pillow, сохраняют исходные пиксели и ориентацию. PDFium-вызовы защищены общей блокировкой и завершаются до HTTP. Координаты областей не формируются; будущий EvidenceRef ссылается на оригинал/версию, известную страницу и OcrResult ID.

Миграция `0002_ocr_results` добавляет assets_file_versions и assets_ocr_results. Оригинал сохраняется в BlobStore и удерживается версией файла. Результат содержит текст, исходную версию/страницу, способ подготовки, SHA-256 и blob отправленной страницы, OCR-профиль, время, длительность, correlation ID и server request ID при наличии. Текст и данные страницы не попадают в repr/CLI/логи. Метаданные содержат только разрешённые поля; ключи подключения не сохраняются.

Ключ совместимости: версия и SHA-256 оригинала + страница + профиль подготовки + OCR-профиль. Последний включает URL, явную ревизию конфигурации, версию протокола и наблюдавшиеся health/model/version/layout; неизвестные сведения остаются null. Это наблюдение health, а не подтверждение серверной версии для каждой страницы. Изменение модели Qwen, промпта извлечения, правил или токена не входит в этот ключ.

SHA-256 отправленных байтов сохраняется для проверки происхождения, но не определяет совместимость: повторная сериализация того же PDF может изменить служебные ID/метаданные. Семантическое изменение подготовки требует нового preparation_profile. При совпадении совместимости возвращается исходный неизменяемый результат вместе с его реальной подготовленной страницей; поздний дубликат не меняет прежний текст.

Чтение/сохранение используют отдельные короткие UoW. Во время HTTP нет открытой предметной транзакции. Сохранение результата, подготовленных байтов и удерживающей ссылки выполняется атомарно; одинаковый ключ сериализуется транзакционной блокировкой. Ошибка другой попытки/профиля не удаляет успешный OCR. После перезапуска новый экземпляр сервиса использует сохранённый текст.

Этот сервис сохраняет производное содержимое и не публикует run/progress/verdict. INT01 соединит его с очередью, lease/heartbeat, проверкой ревизии/run ID/progress_version и Qwen. Эти проверки и реальный повтор Qwen после перезапуска worker остаются отдельной интеграционной приёмкой.

## Ошибки и повторы

OcrFailure передаёт stage=ocr, provider=olmocr, безопасный code, correlation ID, retryable, HTTP status и Retry-After в секундах. PreparationFailure имеет stage=preparing и не приписывает ошибку внешнему провайдеру.

| Причина | Код OCR | Повторяемость |
| --- | --- | --- |
| Тайм-аут / сеть | ocr_timeout / ocr_network_error | Временная |
| 429 / 5xx | ocr_rate_limited / ocr_service_error | Временная, с Retry-After |
| 401/403 | ocr_auth_error | Без автоматического повтора |
| Неподдерживаемый вход / размер | ocr_unsupported_input / ocr_input_too_large | Без автоматического повтора |
| Пустой текст / неверный тип ответа | ocr_empty_result / ocr_invalid_response | Без автоматического повтора |
| Несовместимый профиль клиента | ocr_profile_mismatch | Без автоматического повтора |

Retry-After понимает число секунд и HTTP-дату. Клиент выполняет ровно одну HTTP-попытку: будущий M11 ограничит временные ошибки тремя попытками и задержкой. CLI не делает скрытых повторов. Тело ошибки сервиса и исходное исключение HTTP-драйвера не выводятся. Ошибки Qwen этот адаптер не создаёт и не интерпретирует.

## Диагностика и реальный прогон

Требуются зависимости и миграции по [runtime.md](runtime.md). Команды выполняются на сервере; документы находятся вне Git:

```bash
uv sync --project backend --locked
uv run --project backend python -m app.runtime.cli migrate
uv run --project backend python -m app.runtime.ocr_cli health
uv run --project backend python -m app.runtime.ocr_cli sample '/absolute/path/real-scan.pdf' --page 1
```

CLI выводит только ID, страницу, число символов, профиль, длительность и reused. Для повторного запуска добавить `--file-version-id` из первого ответа; тот же ID с изменённым оригиналом запрещён. Изменение номера страницы начинается с 1; нулевые/отрицательные номера не допускаются. Нативная страница возвращает native_text_characters без запроса OCR.

Для отдельной проверки соединения на реальном PDF с текстовым слоем доступен явный `--rasterize`: только указанная страница преобразуется в PNG с сохранением ссылки на оригинал. Обычная подготовка по-прежнему обходит OCR для нативного текста.

```bash
uv run --project backend python -m app.runtime.ocr_cli sample '/absolute/path/real.pdf' --page 1 --rasterize
# Повторить с возвращённым ID, в том числе после перезапуска процесса/БД:
uv run --project backend python -m app.runtime.ocr_cli sample '/absolute/path/real.pdf' --page 1 --rasterize --file-version-id <UUID>
```

**Фактический прогон 10.10.2026:** пользователь предоставил реальную выписку ЕГРН вне репозитория. PDF — 1 052 781 байт, 17 страниц; все страницы дали нативный текст. Обычная подготовка первой страницы вернула 2334 символа без OCR. Отдельная PNG-копия первой страницы прошла настоящий POST `/ocr` без токена: 2632 символа, около 18,2 секунды; текст/оригинал/производная страница сохранены в локальном PostgreSQL вне Git. FileVersion ID — cfc95813-a134-4c1a-a2db-69b74eff3b88, OcrResult ID — c0d96f13-5731-4dcb-9ffe-650ff08bc0f5. Новый процесс и повтор после перезапуска PostgreSQL вернули тот же ID и reused=true. Полнота и точность распознанных предметных полей не оценивались; это проверка подключения/хранения/повтора.

63 backend-теста проверяют HTTP/multipart/text, токен и тайм-аут, безопасные ошибки/Retry-After, отсутствие клиентских retry, границы CLI, миграции/источники/cache, конкурентное сохранение, rollback и отсутствие транзакции во время HTTP. MockTransport и непрозрачные in-memory байты используются только в контрактных тестах; успешный запрос выше выполнен на реальном документе. Публичные endpoints/OpenAPI не изменились. Docker, настоящие сканированные многостраничные PDF/JPG, восстановление очереди/worker и OCR → Qwen → UI остаются в последующих проверках.
