# Кейс 3 — коллаборация двух участников

Редакция 3, 10.10.2026. Основа — [specs.md](specs.md) и [case_3.md](case_3.md). Владелец файла — **B**; A передаёт обновления на сверках. CON01 сохранена коммитом ea1c5fc и отправлена пользователем; INF01 реализована в backend/INF01 и передана на проверку. Сессии/права работают; прикладные операции после разрешённого доступа пока отвечают 501. Проверка Docker-контейнеров и совместная приёмка остаются впереди.

## 1. Принятые решения и владельцы

**Цель:** за целевые 7–10 часов получить работающий локальный стенд со всем обязательным ядром спецификации. Резерв сначала закрывает обязательные дефекты, затем D01 → D02 → D03. Источники полей и базовый просмотр уже входят в ядро; ручное редактирование чисел и остальные бонусы отложены. Главный риск — концентрация серверных интеграций у A; временные интервалы не являются измеренной оценкой трудозатрат. Расхождение состава команды с ТЗ 3–5 человек остаётся открытым.

| Направление | Ответственный |
| --- | --- |
| M01–M13, M15, миграции, общий Docker Compose | A |
| M14, frontend и его Docker-сборка | B |
| Преднастроенный каталог: три программы, восемь видов и оговорённое расширение ГИМС | B готовит данные; A валидирует и подключает |
| Unit/contract/integration, серверные контракты и устойчивость | A |
| Тестовая матрица, реальные образцы вне Git, E2E, тексты интерфейса | B |
| Шесть обязательных документов и сценарий защиты | B собирает; A пишет технические инструкции |
| Интеграция, итоговая приёмка и защита | Вместе |

Стек и 15 логических модулей сохраняются: FastAPI/Pydantic, SQLAlchemy/Alembic, PostgreSQL, bytea за BlobStore, PostgreSQL-очередь с арендой, отдельный worker, React/TypeScript/Vite, TanStack Query, простые формы/CSS, polling раз в две секунды. OfficeConverter остаётся заменяемым изолированным адаптером; лицензионный вопрос и реальная конверсия DOC/XLS проверяются рано.

**Внешний профиль:** worker готовит содержимое → при необходимости вызывает удалённый olmOCR → M03 сохраняет текст и источник → отдельно вызывается Qwen → backend валидирует JSON, собирает документы и выполняет правила. OlmOcrClient/OcrPort и QwenProvider — отдельные подключения M06, сборка — M15. Нативный текст/ячейки обходят OCR; Office-оригиналы в OCR не отправляются. Сканированный PDF проходит OCR по отдельным страницам. Повтор Qwen/перезапуск используют совместимый сохранённый OCR, без выдуманных координат.

Настройки подключения определены в M15 [спецификации](specs.md):

```dotenv
OLMOCR_BASE_URL=https://ocr.ilons.ru
OLMOCR_API_TOKEN=
OLMOCR_TIMEOUT_SECONDS=300
QWEN_BASE_URL=https://llm.ilons.ru
QWEN_MODEL=Qwen/Qwen3.8-27B
QWEN_CONTEXT_WINDOW_SIZE=262000
ILONS_API_KEY=
```

Qwen generation path/формат/авторизация/тайм-аут уточняются отдельно; OpenAI-совместимость не предполагается. OCR multipart boundary формирует клиент, файл передаётся в поле file, успешный ответ — response.text, при выданном OCR-токене — x-api-token. OCR и Qwen не имеют общего ключа. 300 секунд — клиентский тайм-аут; контекст 262000 — предоставленная, ещё не проверенная настройка. Секреты доступны только серверным процессам, вне браузера, Git и логов. `/ocr/stream` отложен; веса olmOCR, CUDA, vLLM и локальный запуск его сервиса не нужны.

**Локальный профиль:** `MODEL_PROVIDER=local`, Ollama с первоначальным кандидатом `qwen3-vl:4b-instruct`, реальные текст/таблицы/изображения, без обязательных удалённых подключений или скрытого fallback. Текущая среда — около 16 ГБ RAM/12 логических CPU; скорость и совместный расход памяти Compose проверяются реальным малым вызовом.

**Материалы:** документы и производные результаты остаются вне Git; синтетические документы пока не используются. B ведёт покрытие доступных реальных материалов. Нет образца — проверка не выполнена; качество на отсутствующих/закрытых материалах организатора неподтверждено. Каталог, схемы, промпты и текстовая тестовая матрица сохраняются в репозитории.

**Работа в Git:** собственные клоны, короткие ветки `backend/<ID>` / `frontend/<ID>`, PR с проверкой вторым участником. По указанию пользователя завершённая задача фиксируется коммитом после проверок; ограничения приёмки сохраняются в записи задачи. Сверки каждый час и на контрольных точках; изменения API согласуются до изменения потребителя. Участие обоих отражается осмысленными коммитами, ориентир ≥15 не повод имитировать историю. Колонка ветки/PR заполняется только после их реального создания.

### Границы D01–D03

**D01. Происхождение каждого поля.** A выдаёт EvidenceRef/SourceLocation, исходный фрагмент и способ получения; B раскрывает все использованные источники и открывает нужную страницу/ячейку. Конфликтующие значения не скрываются. Отсутствующее поле показывается как «не найдено». Подсветка области доступна только при достоверных координатах; иначе переход к странице/ячейке и фрагмент. Хранение происхождения и базовый просмотр входят в P0, удобный полный сценарий — в D01.

**D02. Проблемы с действиями.** Одна панель объединяет файлы, логические документы и пакет: критичность, объект, объяснение, источники, следующий шаг. Одинаковая проблема на нескольких уровнях показывается один раз со всеми связанными объектами. Рекомендации — серверные шаблоны по кодам проблем, без дополнительной модели. B показывает фильтры и действия «Загрузить документ», «Открыть источник», «Исправить тип», «Повторить проверку», «Уточнить правило», «Добавить в запрос на доработку». Действия вызывают существующие команды; вердикт меняется после пересчёта. Настройки и технические сбои остаются внутренними задачами.

**D03. Протокол и черновик запроса.** A добавляет сервис внутри M10 за заменяемым интерфейсом рендера, без повторного расчёта правил. Протокол — скачиваемый HTML с печатной вёрсткой/PDF через браузер: заявка, программа, дата, ревизия, состав, правила, замечания, источники и решение при наличии. Неполный отчёт отмечается предварительным. Черновик сохраняется отдельно со ссылкой на исходный отчёт; специалист выбирает подтверждённые замечания, редактирует текст и выгружает DOCX. После новой проверки видно, что черновик основан на прежней версии. B готовит шаблоны, выбор, редактор и выгрузку. Будущее расширение API: протокол по report ID, создание/редактирование черновика и скачивание DOCX; контракт согласуется до реализации потребителя. Итоговый текст проверяет специалист; отправка заявителю не входит в задачу.
